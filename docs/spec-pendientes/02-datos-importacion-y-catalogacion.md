## Reglas comunes y dependencias

### Fundamentos de ejecución

- **F0 — Supabase local y pruebas:** requisito de integración para todas las unidades. Usar el stack local real, usuarios A/B de prueba, JWT reales y Storage privado cuando corresponda. F0 se especifica fuera de este archivo; no se instala aquí. La [CLI de Supabase](https://supabase.com/docs/guides/local-development/cli/getting-started) permite ejecutar el stack local con contenedores. Ninguna prueba necesita un proyecto remoto ni leer el `.env` de la biblioteca personal.
- **F1 — Datos y proveedores:** importación, revisión de colección y catálogo bibliográfico compartido. Autorización en cada entrada, RLS, FK de propietario y límites son requisitos transversales, no una fase de seguridad que se pueda omitir. Las nuevas tablas privadas deben estar cubiertas por políticas antes de habilitar escrituras.
- **F2 — UX:** interfaces de revisión, conflictos, progreso, mapeo y cancelación. Este archivo define sus contratos y decisiones; la especificación visual accesible se coordina con F2.
- **F3 — Lectura y colección física:** futuras lecturas, préstamos, notas/etiquetas/valoración, series y ubicación. El modelo de ejemplares U-DAT-06 debe estar disponible antes de estas funciones. No se crean esas funciones mediante esta especificación.
- **F4 — Operación:** scheduler/ejecución de trabajadores, presupuesto, retención y eliminación de cuenta, respaldo administrativo y observabilidad. La aplicación no presupone que esos servicios estén contratados o configurados.

F0 se concreta en `U-INF-01…07`: las pruebas de este archivo consumen el runner/DDL canónico de `U-INF-04` y los fixtures Auth/Storage de `U-INF-05`. El proyecto local propuesto es `biblib-local`, API `55321` y DB `55322`; el bucket privado `biblib-test-assets` es exclusivamente fixture. La autoridad de migraciones sigue siendo Drizzle: no crear una segunda secuencia de migraciones de dominio en `supabase/migrations`. Los nombres/puertos productivos no se derivan del fixture.

La ampliación de fuentes ISBN se define en `U-BIB-01…05`, no en este archivo: Open Library y BNE como base gratuita; Google Books solo opt-in tras revisar y aprobar condiciones/cuota. U-BIB-01 fija contrato/orquestador, U-BIB-02 adaptadores OL+BNE, U-BIB-03 Google opt-in, U-BIB-04 procedencia/UI/migración de fuentes y U-BIB-05 integración de los flujos y pruebas. U-DAT-05 aporta coordinación de cuota/caché y U-DAT-10 la política técnica de assets; no eligen otro proveedor ni un camino alternativo para altas, importaciones o recuperación.

### Invariantes que deben sobrevivir a todas las unidades

1. El propietario procede de la sesión o de una fila de trabajo autorizada y reclamada por un trabajador interno. Ningún DTO de cliente puede elegir `user_id`, claims RLS, una ruta de Storage ni un identificador de trabajador.
2. Toda FK entre datos privados incluye propietario. Una entrada de A que cite una entidad de B devuelve un error genérico autorizado sin confirmar su existencia ni cambiar filas de B. La bibliografía privada no se convierte en un catálogo público compartido.
3. Las mutaciones observables comparan la versión del recurso y, cuando afectan a la colección, la revisión del conjunto. Las restauraciones generan tokens nuevos incluso al recuperar los mismos IDs; nunca se reutiliza una versión exportada como autorización de escritura.
4. La idempotencia se limita a `(propietario, operación, clave)` y al hash de su entrada canónica. Una clave repetida con otra entrada produce conflicto; una repetición idéntica recupera el resultado durable. No se promete ejecución exactamente una vez de un proveedor que no la ofrece.
5. Red, decodificación de archivos y enriquecimiento quedan fuera de transacciones de dominio. Los pasos tienen límites de filas, bytes, tiempo y reintentos. Un resultado parcial se describe como parcial; una caída no equivale a «no existe portada».
6. Los datos activos no se sustituyen hasta validar y confirmar el conjunto. La predeterminada local permanece protegida y los IDs reconocidos de la misma cuenta se conservan cuando sea seguro; cualquier reasignación queda en un informe privado recuperable.
7. Los registros operativos contienen IDs técnicos, duración y códigos; no títulos, ISBN, consultas privadas, filas CSV, fotos, tokens, URL firmadas ni cuerpos del proveedor. La retención y la eliminación de cuenta incluyen staging, snapshots, trabajos, fuentes y assets, no solo `books`.
8. La simulación de red se inyecta en pruebas, no mediante parámetros de producción que permitan elegir un host. Las pruebas bloquean salidas externas por defecto y verifican Auth/RLS reales localmente.

### Contratos transversales propuestos

Mantener `ActionResult<T>` para resultados esperados. Extender los códigos actuales con `REVISION_CONFLICT`, `PREVIEW_EXPIRED`, `IDEMPOTENCY_CONFLICT`, `JOB_CONFLICT`, `JOB_EXPIRED`, `LIMIT_EXCEEDED`, `MANIFEST_MISMATCH`, `MAPPING_REQUIRED`, `UNSUPPORTED_FIELDS` y `ASSET_REJECTED`, según la unidad. Un error contiene mensaje en español, `retryable`, `correlationId` opaco y, solo para el dueño, incidencias de campo acotadas. Las rutas HTTP los traducen a 400/401/404/409/410/413/422/429/503 según el contrato; no devuelven SQL ni errores internos.

`CollectionRevision` será un token opaco emitido por servidor. Un hash de JSON enviado por el navegador no sustituye esta revisión. `Book.version` continuará protegiendo una ficha; no representa la revisión de estanterías ni de una importación completa.

Las tablas nuevas usarán UUID, `created_at`, `expires_at` donde proceda, propietario y versiones. Las cantidades y tamaños son límites de diseño iniciales medibles; cualquier aumento exige pruebas y configuración, no una decisión del cliente. Un límite rechazado nunca recorta registros.

Separar cuatro versiones: **backup `formatVersion:2`** para el nuevo payload portable, **manifest `bundleVersion:1`** para agrupar partes, **`catalogue.schemaVersion:2` opcional** para procedencia ampliada de U-BIB y **`record.version` UUID** como token vigente de edición. La ausencia de versión interna de catálogo significa metadata legacy; no autoriza perderla. Conservar lectores legacy/v1. Nuevas notas/etiquetas/valoraciones y lecturas F3 entran como campos opcionales declarados y validados del formato v2, asociados a ejemplares; un lector que no los soporte debe rechazar con explicación o preservarlos mediante extensión opaca explícitamente permitida y acotada. Nunca usar el stripping silencioso de campos desconocidos como una migración de backup.

`isbnVerified` mantiene su significado actual: una persona comprobó el ISBN de la edición física. El checksum se deriva aparte como `checksumValid` o resultado de validación; una normalización o coincidencia de proveedor no marca verificación humana.

Todos los casos de aceptación que citan «111 registros» usan un fixture **sintético**, con 102 ISBN de prueba válidos y 9 identificadores manuales, estructura/procedencia/estados equivalentes y sin títulos, fotos ni datos de la biblioteca personal. Un ensayo del JSON personal requiere opt-in privado explícito, fuera de CI, sin incorporarlo a fixtures ni logs.

**Esfuerzo:** S = acotado, aproximadamente hasta dos jornadas; M = varias jornadas; L = cambio de modelo o varios recorridos con migración. Son tamaños relativos, no un compromiso de calendario. Incluyen pruebas y recuperación; las olas y el calendario los decide la coordinación.

### Semántica de fechas editoriales

El modelo conserva el texto original `publish_date` de la fuente y puede añadir `normalizedDate` y precisión `year | month | day | unknown` solo cuando sean explícitos. «1997» no se transforma en «1 de enero de 1997», ni se decide el orden día/mes de una fecha ambigua sin evidencia. Listado, orden, formulario y exportación conservan esa precisión y dejan visible el original cuando no se puede normalizar. Las fechas civiles de préstamo y los timestamps UTC de eventos son tipos distintos.

## U-DAT-01 — Confirmación vinculada a una revisión de la colección

**Objetivo y estado actual.** Evitar que un reemplazo confirmado sobre una vista previa antigua elimine libros añadidos o corregidos después. Hoy el bloqueo serializa la escritura final, pero no comprueba el estado que revisó el usuario.

**Alcance.** Revisión por usuario para cambios de libros y estanterías; vista previa servidor con plan y hash de entrada; confirmación condicional e idempotente. Mantener la revisión local inmediata para errores de archivo. Excluye deshacer y trabajos largos, cubiertos más adelante.

**Archivos propuestos.** `lib/db/schema.ts`, nueva migración `drizzle/<n>_library_revision.sql`, `lib/db/library.ts`, `lib/import-plan.ts`, `app/actions/import-preview.ts`, `app/actions/library.ts`, mutaciones de libros/estanterías y `app/settings/page.tsx`. Añadir pruebas de revisión y entradas concurrentes bajo F0.

**Modelo y contratos.** `library_state(user_id PK, revision UUID, updated_at)` y `import_previews(id, user_id, revision, input_digest, mode, rules_version, plan, expires_at)`. El plan es privado y resume altas, conservados, omitidos, reasignaciones y eliminaciones; el JSON original queda en staging privado si debe persistirse. Propuesta inicial de caducidad: 30 minutos, configurable.

```ts
prepareImportAction(input: unknown, mode: "merge" | "replace"):
  Promise<ActionResult<{ previewId: string; revision: string; digest: string; expiresAt: string; plan: ImportPlan }>>
confirmImportAction(input: { previewId: string; expectedRevision: string; idempotencyKey: string }):
  Promise<ActionResult<{ operationId: string; status: "queued" | "committed" }>>
```

El servidor vuelve a cargar y validar su entrada almacenada y su plan. Bajo el mismo bloqueo de colección compara revisión, modo, versión de reglas y caducidad; ninguna opción enviada al confirmar cambia silenciosamente un plan anterior. `REVISION_CONFLICT` conserva el archivo y ofrece revisar diferencias; no existe `force=true`. La confirmación de un nuevo plan es explícita. `PREVIEW_EXPIRED` exige regenerar revisión; `IDEMPOTENCY_CONFLICT` no ejecuta nada.

La revisión debe cambiar dentro de la transacción de cualquier mutación de dominio, incluida la escritura autorizada directa por SQL/RPC y un cambio de portada. U-DAT-01 deberá garantizar un protocolo de bloqueo único antes de escribir: RPC controlada con permisos mínimos o guardas DB equivalentes. No basta con incrementar un contador desde la UI. Deben evitarse caminos que escriban fuera del protocolo y probarse interbloqueos/reintentos sin pérdidas; backfills administrativos requieren una ventana coordinada y renovación de revisión.

**Aceptación y pruebas.** Dos sesiones de A: preparar reemplazo, añadir libro en la otra y confirmar debe devolver conflicto sin eliminar nada; igual con cambio de estantería, estado o portada. Una mutación de B no invalida la revisión de A. Confirmar dos veces la misma clave devuelve una operación/resultado único; clave igual con modo/archivo distinto falla. Probar con Auth/PostgREST local real la imposibilidad de alterar `library_state` o confirmar una preview ajena, incluida su enumeración. Simular proveedor lento y una escritura entre enriquecimiento y commit. Tras conflicto, el borrador y la selección persisten, pero una confirmación antigua nunca adquiere efecto por reintento automático.

**Migración, backup y despliegue.** Crear estado/revisión para cada usuario existente y lazily para cuentas nuevas; registrar toda escritura antes de activar CAS. Los 111 libros del JSON legacy siguen siendo válidos; su falta de revisión no se interpreta como permiso para reemplazar. El contenido de backups no cambia en esta unidad. Habilitar por entorno y retirar gradualmente la firma antigua de reemplazo; mientras exista, debe pasar por el mismo mecanismo servidor. Recuperación: desactivar nuevos reemplazos y conservar previews para diagnóstico, sin rebajar validación de versión. **Tamaño M.**

## U-DAT-02 — Versiones anteriores y deshacer recuperable

**Objetivo y estado actual.** Recuperar una colección reemplazada por error sin depender de que se descargara una copia justo antes. Hoy la transacción evita escrituras parciales, pero un reemplazo correcto no tiene deshacer persistente.

**Alcance.** Snapshot automático previo a reemplazo y previa restauración/deshacer; historial privado con fecha, motivo, cantidades y caducidad; restauración completa con revisión y plan. Excluye historial ilimitado, sincronización entre cuentas y reversión automática de cambios posteriores por campo.

**Archivos propuestos.** Nuevos `lib/library-snapshots.ts`, `app/actions/library-snapshots.ts`, tablas/migración de snapshots, integración en el publicador base de U-DAT-03 y sección de historial en Ajustes. Esta unidad restaura una colección capturada sin depender del manifest multipart de U-DAT-04. Coordinar F4 para purga y cuotas.

**Modelo y contratos.** `library_snapshots(id, user_id, source_operation_id, captured_revision, schema_version, state, counts, expires_at, digest)` y entradas/chunks privados por snapshot. No usar un JSON gigante en una sola fila; conservar filas o chunks acotados con hashes. La versión del formato es independiente de la versión de una ficha.

```ts
listLibrarySnapshotsAction({ cursor, limit }): Promise<ActionResult<SnapshotPage>>
previewSnapshotRestoreAction({ snapshotId }): Promise<ActionResult<ImportPreview>>
restoreSnapshotAction({ previewId, expectedRevision, idempotencyKey }): Promise<ActionResult<OperationRef>>
deleteLibrarySnapshotAction({ snapshotId, expectedVersion }): Promise<ActionResult<void>>
```

El snapshot anterior y la publicación de datos nuevos deben confirmarse en la misma transacción final, o el snapshot debe estar probado completo contra la misma revisión antes de permitirla. Si capturarlo falla, no reemplazar. Al deshacer tras cambios posteriores se muestra una nueva comparación; no se borran esos cambios usando la confirmación vieja. Si el usuario confirma restauración completa, crear antes otro snapshot del estado que va a sustituirse. No reutilizar tokens de `Book.version`.

Propuesta técnica inicial: snapshots de operaciones destructivas retenidos 30 días y hasta una cuota visible por cuenta. F4 fija capacidad/retención antes del despliegue; agotar la cuota bloquea la operación destructiva o exige liberar capacidad de forma explícita, nunca borrar el último respaldo silenciosamente. La cancelación/eliminación de cuenta elimina también snapshots y blobs asociados según su procedimiento.

**Aceptación y pruebas.** Reemplazar A crea exactamente un snapshot consistente y B no puede listar, descargar ni restaurarlo. Introducir un fallo entre captura y publicación debe conservar la colección original, sin snapshot anunciado como válido de una captura parcial. Deshacer devuelve datos y referencias, conserva IDs propios disponibles y genera versiones nuevas. Una segunda pestaña que edite antes de confirmar provoca conflicto. Probar caducidad, cuota agotada, eliminación de snapshot mientras se prepara una restauración y reintento con respuesta perdida. Integración con Auth/Storage local real cuando haya blobs; mocks de red no afectan la validez del snapshot porque el proveedor no participa en su contenido.

**Compatibilidad y recuperación.** No inferir historial anterior al despliegue. Importar v1 no crea ficticiamente una versión previa del pasado; su primera sustitución sí captura el estado actual. El backup portable incluye por defecto la colección activa, no todo el historial privado; exportar un snapshot es una acción separada. Un ID global ocupado por otra cuenta requiere conflicto genérico o reasignación informada, sin revelar su titular. Desplegar inicialmente con captura y listado, habilitar restauración tras ensayo. Desactivar la UI no borra snapshots; una restauración administrativa sigue el respaldo de F4 y no SQL inverso improvisado. **Tamaño L.**

## U-DAT-03 — Trabajos persistentes de importación y enriquecimiento

**Objetivo y estado actual.** Cerrar o recargar la página sin perder el progreso y distinguir completado, reintentable y sin resultado. Los lotes actuales dependen de que la página solicite el siguiente; no son una cola persistente.

**Alcance.** Ejecución durable de validación, staging, publicación y portadas; consulta/reanudación desde cualquier sesión del dueño; reintentos por elemento, pausa y cancelación. Todos los flujos bibliográficos usan el mismo orquestador U-BIB y las políticas por proveedor de U-DAT-05; no mantienen consultas directas de un proveedor aparte. Excluye inferir éxito por haber enviado una petición, prometer ejecución externa exactamente una vez o contratar una cola externa sin necesidad.

**Archivos propuestos.** `lib/jobs/{contracts,repository,worker}.ts`, `lib/import-publisher.ts`, `app/actions/library-jobs.ts`, una entrada interna de ejecución protegida, runner local, tablas `library_jobs`/`library_job_items`, componentes de estado y pruebas de trabajadores concurrentes. Extraer un publicador interno para un payload canónico validado: bloqueo, CAS, mapeo de IDs, SQL set-based y resultado durable sin red; U-DAT-02 le añade snapshot y U-DAT-04 conjuntos multipart. El scheduler de despliegue pertenece a F4; Postgres y un ejecutor existente bastan para la primera versión.

**Contratos y estado.** Trabajo con `kind`, `contract_version`, `owner`, `idempotency_key`, `input_digest`, `expected_revision`, `state`, `cursor`, cantidades, `next_attempt_at`, `lease_until`, `lease_token`, `fencing_number`, `expires_at` y versión. Estados: `queued → running → waiting_retry/needs_review/paused → succeeded/partially_succeeded/failed/cancelled/expired`. Publicación metadata e imágenes tienen fases/resultados distintos: una portada pendiente no revierte una importación ya publicada.

Acciones: `startImportJobAction({previewId,idempotencyKey})`, `startCoverJobAction({scope,idempotencyKey})`, `getLibraryJobAction({jobId})`, `pauseLibraryJobAction({jobId,expectedVersion})`, `resumeLibraryJobAction(...)` y `cancelLibraryJobAction(...)`, todas `ActionResult`. Devuelven IDs y progreso confirmado, no una cuenta inventada de elementos todavía en memoria. Cada item tiene unicidad `(job_id, item_key, phase)`, snapshot/version de destino y resultado durable.

**Ejecución acotada.** Primera configuración: hasta 20 elementos o 20 segundos por paso; fetch externo con timeout máximo de 8 s y presupuesto restante; escritura en transacción corta sin red. Reclamar con operación atómica/`FOR UPDATE SKIP LOCKED`; lease inicial de 60 s y renovación antes de agotar margen. Cada actualización comprueba token/fencing vigente. Un trabajador detenido más allá del lease no puede publicar después de que otro lo reclame. El tiempo DB es autoridad para caducidad, no el reloj del navegador. El acceso interno no acepta un propietario del cuerpo HTTP: obtiene el dueño de la fila reclamada y revalida su ciclo de vida antes de cada escritura.

**Ciclo de vida mínimo previo a la supresión completa.** Esta unidad añade la guarda de cuenta activa y la autorización del worker dentro del protocolo de escritura, con un estado local real de prueba que puede pasar a bloqueo. La prueba de que un worker tardío no recrea datos usa esa transición y no afirma que ya exista el flujo completo de eliminación. U-OPS-03, después, entrega solicitud, limpieza integral y revocación; integra y amplía estas pruebas. DAT03/DAT10 no dependen de que esa UI exista y no crean un ciclo con OPS03.

La infraestructura privilegiada solo reclama/ejecuta trabajos mediante permisos mínimos o funciones auditadas con `search_path` fijo; nunca entrega `service_role` al cliente. Los retries usan backoff con jitter, límite de intentos y `Retry-After`; «no encontrado» es distinto de timeout/cuota. Pausar evita reclamar el próximo paso; cancelar durante la publicación atómica no puede cortar su transacción a medias. Una solicitud de cancelar debe responder si llegó antes o después del punto de publicación. Los libros modificados manualmente se omiten usando versión y preimagen, como en recuperación actual.

**Aceptación y pruebas.** Crear, recargar y continuar con Auth local real conserva trabajo y cantidades. Dos trabajadores reclaman el mismo item: solo uno puede confirmar; matar el primero después del fetch y antes de persistir permite recuperar sin duplicar libros. Matarlo después del commit y perder la respuesta devuelve el mismo resultado al consultar. Probar expiración de lease, cancelación en cada fase, caída del scheduler, HTTP 429/503/JSON roto y reanudación tras horas. A no puede usar IDs de B ni invocar la ruta interna. Un borrado de cuenta marca la ejecución como no autorizada/expirada y un worker antiguo no recrea sus datos. La red de las pruebas siempre usa mocks, incluida la comprobación de que no hay fetch de ISBN manual.

**Migración y rollout.** No convertir estados en memoria del navegador anterior en supuestos jobs completados; ofrecer iniciar un nuevo recorrido que omite cubiertas ya guardadas. Mantener parser v1/legacy y resultados de importación compatibles mediante adaptador temporal. Primero habilitar portadas, después staging/importación. Payload/staging de trabajos terminados: propuesta de 7 días; resumen sin contenido: 30 días, supeditado a F4 y visible. Al desactivar workers, detener reclamaciones, esperar/expirar leases y dejar consultables los resultados; no borrar trabajos activos. **Tamaño L.**

## U-DAT-04 — Restauración de todas las partes con staging y publicación atómica

**Objetivo y estado actual.** Restaurar un respaldo grande como una sola operación revisable. Hoy cada parte v1 es válida, pero hay que reemplazar con la primera y fusionar las demás; una interrupción puede dejar una colección parcialmente restaurada.

**Alcance.** Selección de todas las partes, manifest verificable, staging privado durable, validación cruzada, plan conjunto y único commit sobre la colección. Excluye publicar cada parte por separado bajo una etiqueta engañosa de atomicidad y elegir generaciones/punteros activos sin medir su necesidad.

**Archivos propuestos.** `lib/library-export.ts`, `lib/import-manifest.ts`, `lib/import-staging.ts`, acciones de sesiones de restauración, publicador DB set-based, nuevas tablas staging, componentes de selección múltiple y pruebas de conjuntos. Mantener los exports/lectores v1.

**Formato propuesto.** Manifest `{kind:"biblib.backup-set",bundleVersion:1,...}` con `exportSetId`, `exportedAt`, `payloadFormatVersion`, lista ordenada de `{partId,index,byteLength,sha256,counts}`; `counts` es por tipo de entidad, con libros/estanterías en v1 y obras/ediciones/copias/estanterías en v2, cantidades globales únicas y una suma del conjunto. `bundleVersion:1` no es `formatVersion:1`: el payload nuevo será `formatVersion:2` y se mantienen adaptadores para partes v1. Calcular hashes sobre bytes UTF-8 exactos descargados; no sobre JSON reserializado en otro orden. El manifest comprueba integridad, no firma de autoría. No incluir `user_id` como autorización. Partes actuales v1 pueden asociarse mediante un asistente que genere manifest servidor tras inspeccionarlas; igual fecha no demuestra por sí sola que pertenezcan juntas. U-BIB-04 ya habrá definido el payload v2 canónico y su adaptación legacy; esta unidad no inventa otro esquema v2.

Sesión `import_sessions` con dueño, estado, revisión base, versión de reglas, hash global, expiración y progreso; chunks/filas staging con FK de propietario y claves estables de parte/fila. `beginRestoreSessionAction`, `uploadRestorePartAction({sessionId,partId,bytes/hash})`, `validateRestoreSessionAction`, `prepareRestoreSessionAction` y `commitRestoreSessionAction({sessionId,previewId,expectedRevision,idempotencyKey})`. Cada chunk conserva los límites actuales; límite conjunto inicial propuesto de 10000 libros, 1000 estanterías y 80 MiB, condicionado al benchmark y presupuesto de almacenamiento. No elevarlo sin medición.

**Transporte de partes.** No enviar 8 MiB binarios como un argumento base64 de una sola Server Action: su envoltorio puede superar el límite HTTP. El wrapper de subida divide bytes originales en chunks útiles de hasta 256 KiB, con `partId`, ordinal, total y hash; el servidor limita bytes reales, tamaño acumulado y cantidad antes de persistir. Se usa FormData/Blob o un endpoint de streaming autenticado y acotado, conservando bytes sin reinterpretar UTF-8 entre chunks. Repetir un chunk idéntico es idempotente; otro contenido en el mismo ordinal es conflicto. Se verifica el hash completo de la parte reconstruida antes de parsearla. Ningún chunk individual autoriza ni publica una colección.

Validar todas las partes esperadas, ausencia de partes extra/dobles, hashes, totales, referencias y duplicados globales. Compartir una estantería entre partes es válido solo si su ID y atributos son compatibles; resolver nombres/IDs contradictorios antes de confirmar. Estanterías vacías cuentan. `MANIFEST_MISMATCH` o `LIMIT_EXCEEDED` mantiene intacta la colección activa.

**Publicación medida.** Preparar filas en pasos bounded y publicar bajo bloqueo de colección y CAS de U-DAT-01, usando SQL set-based (`INSERT … SELECT`, borrado/actualización de los datos del dueño y mapeo previo de IDs), sin fetch externo. Capturar snapshot U-DAT-02 coherente y reemplazar en la misma transacción final. Propuesta inicial: `lock_timeout` de 1 s y `statement_timeout` de 5 s, más un presupuesto total de transacción/ejecutor configurado por F4. Medir 100, 1000 y 10000 libros con índices y RLS en Supabase local. Si no cabe, fallar y revertir completamente; conservar staging para reintentar/revisar. No resolverlo con commits parciales ocultos. Conservar predeterminada e IDs propios reconocidos y devolver mapeos/versiones nuevas.

Solo si esas medidas lo justifican se redactará un ADR de generaciones/puntero activo. Ese ADR deberá cubrir PK físicas/IDs lógicos, FK, todas las consultas de libros/estanterías, RLS de historial/staging, editores concurrentes, backups, rollback y migración completa coordinada con U-DAT-06. No es el diseño por defecto de esta unidad.

**Aceptación y pruebas.** Conjunto con 2001 libros en dos partes publica todos juntos; observadores concurrentes ven la colección anterior o la nueva, nunca una mitad. Probar parte ausente, duplicada, corrupta, de otro conjunto, total falso y estantería vacía/compartida. Error en la última sentencia o timeout revierte todo, incluido el indicador de éxito; snapshot y resultado no anuncian un estado parcial. Repetir parte o commit devuelve el mismo resultado; subir el mismo `partId` con otros bytes produce conflicto. Edición de otra pestaña durante staging invalida CAS, conserva staging y exige revisar. Auth/Storage local real para permisos; proveedor simulado y ninguna consulta externa dentro del commit. Registrar tiempos y filas de los tres tamaños, sin datos privados.

**Compatibilidad y recuperación.** Mantener los 111 libros JSON legacy y `manual-...` sin pérdida; una parte v1 sola sigue siendo importable. Exportar un manifest no obliga a nuevos usuarios a compartir backups ni sus fuentes. Primera fase solo valida conjuntos y muestra plan; publicación detrás de flag hasta pruebas de fallo. Sesiones abandonadas expiran, por ejemplo en 7 días, con limpieza por dueño y sin tocar libros activos. Desactivar el flujo conserva descargas v1 y los datos actuales; recuperar desde snapshot o respaldo administrativo según F4. **Tamaño L.**

## U-DAT-05 — Cuota, caché y deduplicación del proveedor entre instancias

**Objetivo y estado actual.** Respetar al proveedor aunque haya varios procesos, importaciones y recuperaciones simultáneas. Hoy los caches/contadores son locales y el importador mantiene su propio intervalo.

**Alcance.** Coordinación compartida usada por el único orquestador U-BIB para búsqueda ISBN/título, importación, recuperación y futuros workers; cuota por proveedor/despliegue y por dueño, caché de metadatos cuyo almacenamiento esté permitido y consultas en vuelo. La selección de fuentes, fallback bibliográfico y reglas OL/BNE/Google pertenecen a U-BIB. Excluye guardar bibliotecas privadas en una caché pública, asumir que acceso gratuito autoriza persistencia ilimitada y comprar Redis/otra cola sin demostrar necesidad.

**Archivos propuestos.** `lib/bibliographic-catalog/{gateway,cache,quota}.ts`, integración con los adaptadores U-BIB y `lib/open-library.ts`/`lib/library-import.ts` durante transición, tablas internas de caché/cuotas y pruebas multiproceso. No crear un segundo subsistema `lib/providers` paralelo al catálogo común. Postgres existente sirve para primera coordinación; justificar otra dependencia solo tras medir contención/volumen.

**Contratos.** El gateway de infraestructura recibe `providerId`, `operationKind`, `licensePolicyVersion`, clave canónica y contexto servidor del orquestador; no expone una acción que permita al cliente saltarse su configuración. Conserva los estados U-BIB `found | notFound | unavailable | rateLimited | disabled | misconfigured`, con `fetchedAt`, `retryAt` y procedencia por campo. Esperar una reserva es un estado del job, no `notFound`. `context` incluye operación/job, nunca un owner elegido por cliente. Una ficha procede de uno o varios proveedores y conserva derechos/restricciones por afirmación; una mezcla no adquiere automáticamente la licencia más permisiva de sus componentes.

Una política servidor versionada por proveedor controla capacidades `cacheMetadata`, `persistMetadata`, `rehostCover`, `exportMetadata`, `backupAsset` y `offlineUse`, plazos, atribución y ámbito por credencial. Si la capacidad no está aprobada, se deniega; `misconfigured` no se convierte en ausencia de ficha ni justifica usar una cuenta de pago ajena. Las claves de caché incluyen proveedor, política/licencia, credencial/ámbito cuando corresponda, versión de schema y parámetros relevantes. Revocar/cambiar política invalida entradas incompatibles y bloquea su reutilización; su limpieza sigue los plazos aprobados. No habilitar caché persistente, backup ni uso offline indiscriminados de Google Books.

Las filas compartidas no contienen propietarios, notas, estados de lectura, datos de ejemplar ni consultas de texto que revelen información privada. Consultas privadas de texto: caché por dueño o clave HMAC y contenido tratado como privado, nunca visible por API de caché. Cifrado o HMAC de una clave no convierte en públicos sus resultados privados.

Reserva de cuota atómica por proveedor/ámbito mediante fila/función DB; no dormir dentro de la transacción. Para Open Library, empezar con el límite conservador de 1 petición/s por despliegue mientras no exista identificación acordada que permita otra cuota; BNE y Google usan su propia política validada en U-BIB, nunca el límite copiado de OL. Respetar `Retry-After` y cooldown compartido tras 429. La [política de Open Library](https://openlibrary.org/developers/api) exige uso moderado, caché e identificación. Reservas expiran y usan fencing para que un worker tardío no publique una entrada vieja sobre otra reciente. TTL inicial propuesto para OL: ficha 1 h, ausencia 5 min; los demás proveedores requieren su TTL autorizado. No cachear una caída como ausencia. Cuotas por dueño y fair scheduling evitan que una importación grande bloquee búsquedas interactivas indefinidamente.

**Aceptación y pruebas.** Dos procesos Node distintos contra Supabase local solicitan el mismo ISBN/proveedor simultáneamente: una consulta en vuelo compartida, resultado equivalente y sin referencias privadas compartidas. Solicitudes a distintos ISBN respetan el intervalo global también entre búsqueda/import/portadas. OL y BNE no consumen la misma reserva; Google deshabilitado/ausente de configuración no recibe peticiones ni crea caché persistente. Probar 429 con `Retry-After`, worker muerto tras reservar, carrera de caducidad, cache malformada, cambio de schema/licencia y caída de Postgres: no efectuar una ráfaga externa como fallback. Una política que deniega persistencia impide escribir la ficha o cover en caché, backup y assets aunque otro proveedor permita guardar los suyos. A no puede inspeccionar historial/cuota privada de B ni manipular reservas. El mock registra solo claves ficticias para demostrar frecuencia; red real prohibida. Una cuota agotada produce espera durable o error recuperable, sin perder la importación confirmada.

**Migración y rollout.** Añadir tablas internas sin acceso directo `authenticated`; no migrar caches en memoria. Enrutar primero ISBN, después lotes y título, todos por U-BIB. Mantener fallback genérico y mensajes actuales mediante adaptación de errores. U-BIB coordina la migración del enum actual `catalogue.source` y los adaptadores de backup: DAT no añade BNE/Google como cadenas libres que el schema elimine o rechace. v1/legacy se siguen leyendo como antes; cualquier extensión de fuente requiere versión o adaptador explícito y conserva afirmaciones restringidas fuera de exports no autorizados. Al desactivar gateway compartido, reducir capacidad y parar trabajos antes de cualquier vuelta temporal al control local; no crear dos cuotas simultáneas que dupliquen el límite. F4 fija tamaño máximo, limpieza y observabilidad sin payloads. **Tamaño M.**

## U-DAT-06 — Obra, edición y ejemplar con ISBN opcional

**Objetivo y estado actual.** Representar libros sin ISBN y varias copias de una edición sin simular ISBN ni confundir lectura/ubicación con descripción bibliográfica. Hoy `books` mezcla todo y su unicidad impide dos copias con igual ISBN.

**Alcance.** Separación gradual, privada por usuario, de `works`, `editions` y `copies`; ISBN-13 canónico nullable en edición; identificadores externos y legacy separados. Mantener rutas a fichas por ID de ejemplar, estado y estantería. Excluye un catálogo público de usuarios, deducir automáticamente que dos títulos son la misma obra y añadir préstamos/series/notas sin sus especificaciones F3.

**Archivos propuestos.** `lib/types.ts`, schema/migraciones nuevas, mappers/read models, validadores/acciones y formularios, import/export y pruebas de migración. Cambia todos los consumidores de `Book`; mantener un DTO plano de lectura durante la transición.

**Modelo propuesto.** `works(user_id,id,title,version)`; `editions(user_id,id,work_id nullable,isbn13 nullable,title,authors,publishers,publish_date,pages,language,identifiers,catalogue,version)`; `copies(user_id,id,edition_id,status,shelf_id,edition_verification jsonb,version,legacy_identifier nullable)`. Las FK incluyen propietario. Autoría bibliográfica, editoriales y fecha corresponden a **edición**; autores/editores conservan orden y función y una obra puede ser desconocida sin bloquear la copia. Una edición sin ISBN sigue teniendo UUID. Estado de lectura, ubicación, préstamos, notas, etiquetas y valoración pertenecen por defecto a **ejemplar**; una futura nota de obra necesitará opción y contrato explícitos. Tras el cutover, F3 adaptará mappers/modelos y no volverá a añadir esas columnas a una `books` obsoleta. La unicidad de ISBN no vive en `copies`: para el flujo inicial, una edición canónica por `(user_id,isbn13)` no nulo y varias copias asociadas. Conflictos bibliográficos de ese ISBN se revisan como candidatos; no se crean dos ediciones contradictorias automáticamente. `edition_verification` pertenece a la copia: `{ isbnVerified: false, checkedAt?: string, evidenceRefs?: string[] }`, con falso por defecto y confirmación humana protegida por su versión. `editions.catalogue` solo conserva procedencia bibliográfica y excluye ese indicador físico. El DTO plano `Book.catalogue.isbnVerified` se deriva de la copia, no de la edición compartida; una copia nueva de una edición ya comprobada en otra sigue en falso.

Contratos separados: `createCopyAction({editionId,placement,...})`, `createEditionAction({isbn13:null|string,...})`, `updateEditionAction({editionId,expectedVersion,...})` y `mergeEditionsAction({sourceIds,targetId,expectedVersions,expectedRevision,idempotencyKey})`. Añadir copia es explícito; «ya existe» ofrece abrir ejemplares o añadir otro, nunca lo hace por error. Cambiar una edición compartida por varias copias informa de cuántas afecta. La verificación física de ISBN corresponde al ejemplar/afirmación comprobada, no a todos los usuarios ni automáticamente a todas las copias; mantener migración de `catalogue.isbnVerified` sin ampliarle su significado. El editor plano envía versiones de copia y edición para los campos respectivos; `Book.version` no autoriza por sí solo una actualización de una edición compartida. Cambiarla invalida la revisión de colección y las previews afectadas. Prueba obligatoria: copia A verificada y copia B nueva sobre la misma edición conservan true/false independientes.

**Migración de datos.** Ensayar expandir/backfill/comparar/cambiar lecturas/retirar legacy, con puntos de recuperación. Cada `books.id` se convierte en `copies.id` estable; crear una edición inicial para su ficha y una obra solo si hay evidencia. `manual-...` pasa a `legacy_identifier`; `isbn13 = null`, sin perder el valor original ni usarlo como ISBN. Variantes ISBN-10/13 existentes detectadas durante backfill se presentan como conflicto o se agrupan solo si los campos son compatibles y se conserva el informe. No descartar dos filas antiguas por equivalencia. Versiones nuevas después de backfill; F1 garantiza que todos los caminos usan las nuevas relaciones antes de retirar el índice viejo.

**Backups y transición.** U-BIB-04 introduce antes el esquema portable canónico `formatVersion: 2` con `works`, `editions`, `copies` y `shelves`, mediante un adaptador sobre `books` legacy. No existen dos shapes distintos llamados v2. Antes de separar tablas, el adaptador usa `copy.id = book.id`, `edition.id = book.id` en namespaces de entidad diferentes, `work_id = null` y `works = []`; extrae la verificación física a la copia, conserva el identificador manual en legacy y convierte ISBN válido a la edición. El backfill de esta unidad reutiliza esos IDs; una fusión posterior genera un mapeo explícito. El lector v2 previo a la migración solo acepta estados representables por el esquema legacy y rechaza varias copias por edición u otras secciones aún no soportadas, sin truncarlas. Tras el cambio de modelo se habilita la capacidad completa de v2. Mantener adaptadores de lectura legacy/v1 que creen una copia por fila: el fixture sintético de 111 libros produce exactamente 111 copias, con estado provisional y procedencia. Exportación v1 opcional solo si es representable sin pérdida; con varias copias, fuentes nuevas o datos no representables debe exigir v2, nunca inventar ISBN u omitir copias. No importar `Book.version` como versión vigente. Cada payload v2 declara `requiredCapabilities`; el lector rechaza una capacidad desconocida y valida las secciones antes de escribir. El formato interno del snapshot es independiente.

**Aceptación y pruebas.** Migración local real conserva IDs, ubicación, autores, editoriales, estado, portadas y procedencia del fixture sintético de 111 registros y de fixtures con equivalencias conflictivas. Crear dos copias de un ISBN genera una edición y dos ejemplares, cada uno con ubicación/estado independientes. Un libro sin ISBN puede editarse, exportarse y restaurarse sin identificador falso en el campo ISBN. FKs rechazan referencias privadas de B y merges cruzados. Pruebas concurrentes de crear edición/copia no duplican por reintento. Ida y vuelta v2 conserva todas las entidades, múltiples copias y campos F3 declarados; lector v1 informa incompatibilidad en lugar de truncar. Proveedor simulado nunca acredita verificación física.

**Despliegue y recuperación.** Flag de lectura nueva, comparación de recuentos y canary local/entorno de prueba antes de cambiar escritores. Retener tablas anteriores durante una ventana definida por F4; no prometer vuelta al escritor antiguo después de admitir varias copias sin un export v2 y un plan explícito. Si falla, detener nuevas escrituras y corregir o restaurar el respaldo probado. **Tamaño L.**

## U-DAT-07 — Bandeja de revisión bibliográfica y decisiones masivas

**Objetivo y estado actual.** Resolver de forma trazable libros provisionales, ISBN de referencia, dudas de las fotos y candidatos duplicados. Hoy solo existe un campo de procedencia y un checkbox en cada ficha; no una comparación central.

**Alcance.** Lista paginada de incidencias, filtros por motivo/fuente y resolución, comparación campo a campo, grupos de candidatos y operaciones masivas revisables. Conservar fuente de una afirmación y la decisión humana. Excluye marcar automáticamente una edición física como comprobada por una foto de lomo o ejecutar merges basados solo en similitud.

**Archivos propuestos.** `app/books/review/page.tsx`, componentes de comparativa, `lib/catalogue-review.ts`, acciones, tablas de evidencia/incidencias/decisiones y tests de lotes. Integrar F2 para accesibilidad y F3 para edición/ejemplar.

**Modelo y contratos.** `bibliographic_evidence(owner,id,subject_kind,subject_id,source_kind,source_ref,observed_at,field_claims,confidence_label,version)`; `review_issues(owner,id,reason,entity_refs,state,version)`; `review_decisions(owner,id,issue_id,selected_fields,evidence_refs,actor,decided_at,operation_id)`. Reutilizar procedencia por campo y capacidades de licencia del contrato U-BIB, sin inventar otra lista de proveedores ni persistir respuestas restringidas por aceptarlas en la UI. Guardar fuente fotográfica como referencia privada a un asset del dueño, no ruta pública ni foto original en logs. La confianza se etiqueta `provisional | bibliographic_match | physically_checked`, con alcance y evidencia; no se usa un porcentaje inventado como probabilidad.

Acciones: `listReviewIssuesAction({filters,cursor,limit})`, `compareBibliographicCandidatesAction({issueId})`, `prepareReviewBatchAction({issueIds,proposedDecisions})`, `applyReviewBatchAction({previewId,expectedRevision,idempotencyKey})`. Las decisiones por campo conservan los demás valores. `confirmPhysicalEdition` exige acción explícita de comprobación; aplicar una ficha pública conserva estado provisional. Ignorar una duda no borra su evidencia. Fusionar obras/ediciones y mover copias requiere plan específico con versiones U-DAT-06; si hay discrepancias, abrir resolución, no sobrescribir en silencio.

**Aceptación y pruebas.** Una importación de referencia genera incidencias adecuadas y no 111 comprobaciones físicas falsas. Un lote de hasta 50 decisiones muestra altas/modificaciones/fusiones y requiere confirmación; una versión antigua produce conflicto de esa operación, sin mitad aplicada salvo que el usuario eligiera un modo parcial explícito con informe por fila. Probar dos revisores de la misma cuenta, una fuente eliminada/caducada, candidatos homónimos y autores iguales con obras distintas. Auth local verifica que B no enumera fotos, fuentes ni incidencias de A. Mocks del proveedor presentan ediciones parecidas y datos contradictorios; ninguna selección automática incrementa verificación física.

**Migración y compatibilidad.** La procedencia actual se convierte en evidencia inicial sin fabricar una URL o foto ausente. Los `procedencia.json`/pendientes externos de las fotografías solo se incorporan mediante selección autorizada y validación de asociaciones; no leer ni publicar automáticamente archivos personales del repo. v2 exporta evidencia portable con referencias privadas y manifiesta assets opcionales; no filtra propietario ni fuerza publicar fotos. El lector v1 conserva al menos el resumen compatible y advierte de evidencia no representable. Primero bandeja de solo lectura, después decisiones individuales y finalmente lotes/merges. Retener el historial según F4, con borrado de fuentes personales y cuenta; desactivar sugerencias no modifica las fichas ya revisadas. **Tamaño L.**

## U-DAT-08 — Buscar por título y autor cuando falta ISBN

**Objetivo y estado actual.** Encontrar candidatos bibliográficos sin pedir al usuario un ISBN que desconoce. La búsqueda externa actual solo resuelve ISBN; la búsqueda local por texto ya existe y debe seguir separada.

**Alcance.** Consulta externa paginada por título y/o autor, selección de obra y edición, comparación antes de añadir o vincular a una ficha. Excluye búsqueda mientras se escribe cada carácter, scrapeo HTML, elegir el primer ISBN de una obra como edición física y envío de notas/fotos privadas al proveedor.

**Archivos propuestos.** Adaptador de búsqueda del orquestador U-BIB, API/acción autenticada de búsqueda bibliográfica, `app/books/add/page.tsx`, componentes de resultados/ediciones y tests de contrato. Reutilizar orquestador y gateway U-DAT-05; no crear llamadas directas de UI/importación a OL/BNE/Google ni introducir otro SDK si fetch/schema actuales bastan.

**Contrato.** `searchBibliographyAction({title?:string,author?:string,page:number,limit:10|20,language?:string}) → ActionResult<{queryToken,results,nextPage,totalEstimate?}>`. Entrada al menos tres caracteres útiles, longitudes acotadas, página máxima configurada y búsqueda por envío explícito. Retornar `BibliographicCandidate` con clave de proveedor, nivel `work|edition`, título/autores/idiomas/fecha, identificadores candidatos y URLs permitidas; sin `user_id` ni datos de biblioteca. Separar `loadEditionCandidatesAction({queryToken,workKey,page})` y `prepareCandidateLinkAction({candidateKey,targetCopyId?,expectedVersion?})`; las claves se validan y no son URL arbitrarias.

El orquestador U-BIB selecciona las capacidades de búsqueda textual disponibles sin suponer que todo proveedor ISBN ofrece búsqueda de texto equivalente. Como adaptación inicial, la [Search API de Open Library](https://openlibrary.org/dev/docs/api/search) dispone de `title`, `author`, selección de campos y paginación; por defecto devuelve obras. Pedir campos mínimos y schema tolerante a ausencias, evitando `fields=*`. Un resultado de obra no basta para asignar ISBN a un ejemplar. Se permite elegir «no sé la edición» y crear ficha provisional sin ISBN, que U-DAT-06 representa directamente; antes de esa migración se usa el identificador manual compatible. Los estados `notFound`, `rateLimited`, `unavailable` y `misconfigured` permanecen separados y no provocan selección silenciosa de una edición. Google Books no se invoca por defecto ni para suplir una búsqueda fallida sin su opt-in aprobado.

**Aceptación y pruebas.** Buscar título/autor sin ISBN presenta varios candidatos y permite consultar ediciones antes de guardar. Un homónimo, traducción o fecha distinta no se considera coincidencia segura; la elección no marca físicamente verificado. El botón manual conserva el texto ya introducido. Cancelar una petición o recibir respuesta tardía de otra consulta no reemplaza la selección más reciente. Dos usuarios con la misma búsqueda reciben bibliografía pública equivalente y ninguna indicación de qué tiene el otro. Probar Auth local, paginación, Unicode/tildes, campos ausentes, API que devuelve obra/edición parcial, 429, timeout y red bloqueada con fixtures. No se realizan peticiones externas al importar un CSV salvo que se solicite enriquecimiento.

**Migración, backups y rollout.** Sin cambios obligatorios de dominio si se mantiene DTO provisional; claves/fuentes persistidas se adaptan al modelo de evidencia. v1/los 111 libros siguen leyendo igual; las fichas nuevas sin ISBN se exportan en el formato compatible disponible. Habilitar detrás de flag con presupuesto global y comprobar selecciones ambiguas antes de ofrecer enlace masivo. Si se desactiva, mantener las fichas guardadas y la entrada manual, no borrarlas ni dejar un botón ficticio. **Tamaño M.**

## U-DAT-09 — CSV con mapeo explícito y revisión reutilizable

**Objetivo y estado actual.** Importar catálogos de otras herramientas sin preparar a mano el JSON de BibLib. Hoy solo se acepta su esquema JSON.

**Alcance.** CSV UTF-8, separador coma/punto y coma/tabulador seleccionable, cabecera y previsualización, mapeo de columnas, normalización explícita de autores/estados/estanterías e incidencias por registro. Reutilizar staging, revisión y confirmación; no convertir la selección del CSV en una escritura. Excluye XLSX, macros, detección arbitraria de codificaciones y ejecutar fórmulas o contenido de celdas.

**Archivos propuestos.** `lib/csv-import/{parser,mapping,normalization}.ts`, acciones de sesión CSV, componentes de mapeo y fixtures. Evaluar un parser CSV mantenido por soporte de comillas/saltos de línea/streaming y límites; fijar versión si se incorpora. No escribir un parser basado en `split(',')`. La nueva dependencia requiere justificar tamaño, licencia, mantenimiento y alcance frente a una alternativa existente.

**Contratos.** `inspectCsvAction({sessionId,chunk}) → {headers,sampleRows,detectedDelimiter?,issues}`; `setCsvMappingAction({sessionId,expectedVersion,mapping,mappingVersion})`; `prepareCsvImportAction({sessionId,mode,duplicatePolicy}) → ImportPreview`. Mapeo `sourceColumn → title|authors|isbn|publishers|pages|publishDate|status|shelf|ignore`, con reglas por columna y selección explícita de cualquier campo no conocido. Título obligatorio; ISBN opcional. Reglas de estado requieren tabla de equivalencias visible, sin convertir un valor desconocido en «Leído». Autor compuesto se divide solo con separador elegido; «Apellido, Nombre» entre comillas no debe romperse en dos autores por defecto.

Primera versión: 8 MiB por archivo, 2000 registros y límites de campo del JSON; el conjunto grande pasa por U-DAT-04 y sus límites. Número de fila significa registro CSV, no línea física cuando hay saltos entre comillas. Mantener `source_row_key` durable por sesión/ordinal y hashes de input+mapeo para retries; no regenerar IDs manuales en cada intento. Todos los errores se muestran con código/campo y muestra privada acotada. Importar solo filas válidas exige elección explícita, plan que enumere las omitidas y un informe descargable; por defecto los errores bloquean la confirmación.

**Aceptación y pruebas.** CSV con BOM, comillas escapadas, separador dentro del texto y saltos de línea produce registros correctos; cabecera duplicada o estructura truncada produce incidencia, sin pérdida silenciosa. Mapeo corregido regenera el plan e invalida la confirmación anterior. Reintento no añade dos veces una fila; con U-DAT-06 «otra copia» es política explícita y «omitir existente» sigue disponible. Páginas negativas, estado desconocido y ISBN con checksum erróneo requieren decisión/corrección, no datos inventados. Una celda `=...`, `@...` o texto con SQL nunca se ejecuta; cualquier informe CSV que pueda abrirse en hoja de cálculo escapa fórmulas sin alterar el valor guardado. Auth/Storage local y mocks de enriquecimiento verifican aislamiento, límites, mezcla de fuentes y el mismo CAS que JSON.

**Migración y compatibilidad.** No cambia filas existentes. Guardar perfiles de mapeo solo si el usuario lo pide; son privados y versionados, sin contenido de muestras. La salida canónica alimenta JSON v1/v2 y conserva identificadores legacy; exportación/restauración de la colección no requiere conservar el archivo CSV original. Primero inspección/mapeo sin escrituras, luego importación integrada. Cancelar elimina/expira staging según F4 y nunca toca la colección. Si se desactiva el parser, las fichas ya importadas y las exportaciones permanecen utilizables. **Tamaño M.**

## U-DAT-10 — Almacenamiento opcional y seguro de portadas

**Objetivo y estado actual.** Poder conservar imágenes sin depender permanentemente de URLs externas, cuando su coste y uso lo justifiquen. Ahora se guardan URLs y el navegador solicita las imágenes; no existe un servicio servidor que descargue cualquier URL del usuario.

**Alcance.** Primitivas de assets reutilizables por otros recursos, bucket privado de Supabase, copia de portadas solo cuando la política U-BIB del proveedor/asset autorice rehosting y carga explícita de imagen propia, con cuotas y ciclo de vida. Acceso gratuito a un catálogo no basta para copiar su imagen. Excluye abrir un proxy de URL arbitraria, hacer público el inventario de una cuenta y habilitar procesadores/binarios actualmente denegados sin revisión. El uso actual de URLs permanece como alternativa sujeta a la política aplicable.

**Archivos propuestos.** `lib/assets/{contracts,fetch-policy,image-validation,repository}.ts`, `app/actions/book-cover-assets.ts`, ruta autenticada de lectura, bucket/políticas mediante la autoridad DDL de U-INF-04, jobs de adquisición/purga y tests de red/Storage con U-INF-05. No crear una historia paralela en `supabase/migrations` ni activar el bucket productivo al sembrar `biblib-test-assets`. Avatar reutilizará estas primitivas, pero su UX y políticas de perfil pertenecen a otra unidad. Antes de elegir decodificador, revisar el `sharp` ya presente y su política de instalación; justificar y aprobar técnicamente la ruta soportada, sin cambiarla como efecto lateral de esta especificación.

**Modelo/contratos.** `cover_assets(user_id,id,storage_key,sha256,mime,width,height,bytes,state,source_kind,source_ref,rights_policy_version,attribution,expires_at,version,created_at)` y referencias con FK de propietario desde edición/copia/snapshot. `requestProviderCoverAssetAction({entityId,expectedVersion,providerCoverKey,idempotencyKey})`, `beginOwnCoverUploadAction({entityId,mime,bytes,...})` y `attachCoverAssetAction({assetId,entityId,expectedVersion})`. El servidor deriva bucket/ruta/propietario y consulta derechos vigentes, nunca los acepta de nombres de archivo, claves o un booleano de cliente. Una adquisición no cambia la portada visible hasta validarse y confirmar su versión. Errores: `ASSET_REJECTED`, cuota, proveedor no disponible, conflicto y cuenta en eliminación. Capacidad de rehosting ausente deniega la adquisición antes de la red; la atribución requerida viaja con el asset y su representación.

**Política de red/archivo.** Para adquisición remota, convertir claves de proveedor validadas en hosts HTTPS fijos. No seguir redirecciones por defecto; si se admiten, revalidar cada destino y resolución DNS. Bloquear localhost, redes privadas/link-local, metadata cloud, IPv4 mapeada en IPv6, puertos no autorizados y DNS rebinding; limitar bytes durante streaming, no confiar en `Content-Length`. Propuesta: 5 MiB, 10 megapíxeles y 8 s por descarga. Aceptar JPEG/PNG/WebP tras comprobar MIME, firma y decodificación real; rechazar SVG/HTML/XML, archivos polígotos y bombas de descompresión. El presupuesto de decodificación y metadatos se mide y acota; reencodificar/retirar metadatos solo con procesador habilitado y soportado. No habilitar el almacenamiento hasta disponer de estas defensas. La carga propia recibe las mismas validaciones y no convierte un `content-type` del navegador en prueba.

**Privacidad y vida útil.** Bucket privado, políticas por propietario y lectura mediante endpoint autenticado que comprueba asset/referencia; caché de respuesta privada, sin indexación pública ni listado de hashes globales. Si se usan enlaces firmados, documentar su capacidad de acceso mientras duren y su TTL corto; no prometer revocación inmediata por RLS de una URL ya emitida. La deduplicación inicial es dentro del mismo propietario. Snapshots retienen referencias; la purga no elimina una imagen todavía usada. El borrado de cuenta cancela trabajos, revoca reclamaciones y elimina objetos/filas en pasos verificables; un worker con lease antiguo no vuelve a subirlos. Subidas incompletas quedan en cuarentena y expiran.

**Aceptación y pruebas.** Supabase local real: A puede adjuntar/leer su portada y B no puede obtenerla ni firmar su ruta. Probar permiso de Storage además del de la tabla; conocer un UUID no basta. Google Books o cualquier proveedor con `rehostCover=false` no genera fetch ni objeto, incluso con job antiguo o cliente manipulado; una política que permite rehosting pero deniega backup/offline conserva esas diferencias. Mock de descarga simula redirección a localhost, respuesta lenta, tamaño mentido, DNS cambiante, MIME falso, SVG y archivo con dimensiones excesivas: rechazo sin red hacia esos destinos y sin sustituir la portada actual. Una edición concurrente o cancelación impide adjuntar el resultado tardío. Repetir la adquisición no duplica objetos; matar el worker después de subir y antes de registrar deja un objeto recuperable/purgable, no un enlace roto confirmado. Verificar cuotas, referencias desde snapshots, expiración de licencia, caducidad y eliminación de cuenta sin resurrección.

**Migración, backup y rollout.** No descargar de golpe todas las URLs existentes. Empezar por acción explícita y proveedor/asset con rehosting aprobado; migración opcional por lotes y con presupuesto visible. JSON v1 solo exporta URL/fuente cuando sus derechos lo permiten, avisando si no representa un asset privado portable. Backup v2 puede incluir manifiesto de assets autorizados y archivos separados con hashes/longitudes, nunca una URL firmada caducable como único respaldo. Las imágenes/metadatos de Google Books no entran automáticamente en cache persistente, respaldo, rehosting ni offline: aplicar la capacidad vigente y señalar como no incluidas las restricciones de portabilidad, sin usar otro campo como vía de escape. Restaurar revalida políticas y se hace en staging/cuarentena bajo el mismo control de propietario, con fallback si el usuario decide omitir imágenes opcionales. Desplegar primero validación/cuarentena, luego adjuntos y finalmente copia remota; flag desactivado conserva la lectura autorizada de URLs/assets existentes y detiene adquisiciones. Recuperación/purga se coordinan con F4 y no dependen de hacer público el bucket. **Tamaño L.**

## Secuencia de validación del conjunto

La coordinación fijará olas sobre el grafo de dependencias. Antes de habilitar cualquier operación destructiva durable deben estar F0/F1, CAS de colección y publicación/snapshot probados juntos. U-DAT-05 puede mejorar los flujos actuales antes de los jobs; U-DAT-08 puede usar fichas provisionales antes del modelo completo. U-DAT-06 exige su propio despliegue de datos y no se mezcla incidentalmente con una mejora de importación o portada.

Cada unidad entregará: migración revisable cuando proceda, contrato validado, pruebas negativas con A/B y JWT reales locales, pruebas de carrera y fallo recuperable, ensayo de backup/restore compatible y registro de límites medidos. F4 debe definir retención, cuota, scheduler y borrado de cuenta antes de habilitar persistencia de fotos, staging o historial a largo plazo. Ninguna cifra del informe histórico sustituye estas pruebas futuras ni autoriza a ejecutarlas contra Supabase de producción.
